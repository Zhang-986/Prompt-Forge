# Architecture: DDD (Domain-Driven Design)
为了承载复杂的业务逻辑，必须采用 DDD 分层架构：

| 层级 | 包路径 | 职责 |
|------|--------|------|
| Interface Layer | `com.zzk.interfaces` | Web Controller、DTO、参数校验 |
| Application Layer | `com.zzk.application` | 业务编排、事务控制、DTO 转换、防腐层 |
| Domain Layer | `com.zzk.domain` | **核心业务逻辑**、充血模型、领域服务、领域事件 |
| Infrastructure Layer | `com.zzk.infrastructure` | AI 调用、数据库持久化、缓存、消息队列、外部服务集成 |

# ====== 核心功能模块 ======

## Core Feature 1: The Arena（多模型竞技场）- 深度逻辑约束

### 业务背景
用户输入一套 Prompt 模板（含变量 `{{topic}}`、`{{style}}` 等）和一组变量值，系统需要让 DeepSeek、GPT-4、Claude 等多个模型**同时作答**，供用户对比评估。

### 必须实现的逻辑流 (Strict Flow)

#### Step 1: 输入解析与模板渲染
- `ArenaAppService` 接收请求后，调用 `PromptTemplateEngine` 工具类
- 使用**正则表达式**解析 Prompt 模板中的 `{{xxx}}` 变量占位符
- 用用户传入的 `Map<String, Object>` 进行变量替换，生成最终 Prompt
- **边界处理**：变量缺失时抛出 `VariableMissingException`

#### Step 2: 策略模式路由 (Strategy Pattern)
- 在 `infrastructure` 层定义 `LlmGenerationStrategy` 接口：
  ```java
  public interface LlmGenerationStrategy {
      String getModelId();
      Flux<String> generate(String prompt, GenerationConfig config);
  }
  ```
- 必须实现至少三个策略类：
  - `OpenAiStrategy` (GPT-4/GPT-4o)
  - `DeepSeekStrategy`
  - `ClaudeStrategy`
- **禁止**使用 `if (type.equals("gpt"))` 这种硬编码写法
- 必须使用 `Map<String, LlmGenerationStrategy>` 或 Spring 的 `@Qualifier` + 自动注入实现路由

#### Step 3: 并行编排与资源隔离 (Concurrency)
- **严禁**在循环中串行调用模型（面试红线！）
- 必须创建**自定义线程池** `ThreadPoolExecutor`：
  ```java
  @Bean("arenaExecutor")
  public ThreadPoolExecutor arenaExecutor() {
      return new ThreadPoolExecutor(
          10, 50, 60L, TimeUnit.SECONDS,
          new LinkedBlockingQueue<>(200),
          new ThreadFactoryBuilder().setNameFormat("arena-pool-%d").build(),
          new CallerRunsPolicy() // 拒绝策略：调用者执行
      );
  }
  ```
- 使用 `CompletableFuture.supplyAsync(task, arenaExecutor)` 发起 N 个模型调用
- 使用 `CompletableFuture.allOf(...)` 等待所有结果，或流式聚合

#### Step 4: 熔断降级与限流 (Resilience)
- 集成 **Resilience4j** 实现熔断：
  ```java
  @CircuitBreaker(name = "llmService", fallbackMethod = "generateFallback")
  @RateLimiter(name = "llmService", fallbackMethod = "rateLimitFallback")
  @Retry(name = "llmService", maxAttempts = 3)
  public Flux<String> generate(String prompt) { ... }
  ```
- 熔断配置：失败率 > 50% 时熔断，等待 30s 后半开
- 限流配置：每秒最多 100 次请求
- **降级兜底**：返回友好提示 "【模型繁忙，请稍后重试】"

#### Step 5: 流式分发 (SSE Streaming)
- Controller 必须返回 `SseEmitter` 或 `Flux<ServerSentEvent<T>>`
- 当任意模型产生输出时，封装为 Event 实时推送：
  ```json
  {
    "modelId": "gpt-4",
    "content": "这是",
    "sequence": 1,
    "finished": false
  }
  ```
- 实现"多窗口同时打字"的实时效果
- 支持客户端主动断开连接的优雅处理

## Core Feature 2: The Versioning（Prompt 版本树）- 深度逻辑约束

### 业务背景
Prompt 需要像 Git 一样管理。修改不是覆盖，而是"提交（commit）"。支持版本回溯、分支对比。

### 必须实现的逻辑流 (Strict Flow)

#### Step 1: 聚合根设计 (Aggregate)
- **Prompt** (Aggregate Root)：
  ```java
  public class Prompt {
      private Long id;
      private String name;
      private Long latestVersionId;  // HEAD 指针
      private Long creatorId;
      private LocalDateTime createdAt;
  }
  ```
- **PromptVersion** (Entity)：
  ```java
  public class PromptVersion {
      private Long id;
      private Long promptId;
      private String content;
      private String variables;  // JSON: {"topic": "string", "style": "enum"}
      private Long parentId;     // 父版本 ID，形成链式结构
      private String commitMessage;
      private Long authorId;
      private LocalDateTime createdAt;
  }
  ```

#### Step 2: 提交逻辑 (commit operation)
- 调用 `PromptDomainService.commit(promptId, newContent, parentVersionId, commitMessage)`
- **Diff 检查**：对比 `newContent` 与 `parentVersion.content`
  - 如果完全一致 → 抛出 `NoChangeException("内容无变化，无需提交")`
  - 可选：生成 Diff 摘要存储（便于展示变更历史）
- **分布式锁**：使用 Redis 分布式锁防止并发提交冲突
  ```java
  @DistributedLock(key = "'prompt:commit:' + #promptId", waitTime = 5, leaseTime = 30)
  public PromptVersion commit(...) { ... }
  ```
- **链式存储**：INSERT 新记录，设置 `parentId`
- **HEAD 更新**：更新 `prompts.latestVersionId` 指向新版本

#### Step 3: 数据不可变性 (Immutability)
- `prompt_versions` 表数据**绝对禁止 UPDATE**，只能 INSERT
- 这是 Event Sourcing 思想的体现，便于审计追溯

#### Step 4: 版本树查询
- 支持 `getVersionHistory(promptId)` 获取完整版本链
- 支持 `getVersionDiff(versionId1, versionId2)` 对比两个版本差异
- 支持 `rollback(promptId, targetVersionId)` 回滚（本质是创建新版本指向旧内容）

## Core Feature 3: 缓存架构（Redis 多级缓存）- 新增亮点

### 业务背景
Prompt 模板会被高频读取，需要高性能缓存架构。

### 必须实现的逻辑

#### 多级缓存设计
```
请求 → Caffeine 本地缓存(L1) → Redis 分布式缓存(L2) → MySQL
```

- **L1 本地缓存**：Caffeine，容量 1000，过期时间 5 分钟
- **L2 分布式缓存**：Redis，过期时间 30 分钟
- 使用 `@Cacheable` + 自定义 `CacheManager` 实现

#### 缓存一致性
- 写操作时使用 **Cache-Aside 模式**：先更新 DB，再删除缓存
- 防止缓存击穿：热点 Key 使用互斥锁
- 防止缓存穿透：布隆过滤器 or 缓存空值
- 防止缓存雪崩：过期时间加随机值

---

## Core Feature 4: 用户与权限（多租户隔离）- 新增亮点

### 业务背景
企业级平台需要支持多团队协作，数据隔离。

### 必须实现的逻辑

#### RBAC 权限模型
- **用户(User)** → **角色(Role)** → **权限(Permission)**
- 预设角色：`ADMIN`（管理员）、`MEMBER`（成员）、`VIEWER`（只读）

#### 多租户设计
- 每个 Prompt 归属于一个 **Workspace（工作空间）**
- 使用 `TenantContext` (ThreadLocal) 存储当前租户 ID
- MyBatis-Plus 拦截器自动填充租户条件

#### 接口权限校验
```java
@PreAuthorize("hasPermission(#promptId, 'PROMPT', 'WRITE')")
public void updatePrompt(Long promptId, UpdatePromptCmd cmd) { ... }
```

---

## Core Feature 5: 任务队列与异步处理 - 新增亮点

### 业务背景
批量测试、大规模评估等耗时任务需要异步处理。

### 必须实现的逻辑

#### 消息队列集成
- 使用 **RocketMQ** 或 **Redis Stream** 作为任务队列
- 任务类型：`BATCH_ARENA`（批量竞技）、`EXPORT_REPORT`（导出报告）

#### 任务状态机
```
PENDING → RUNNING → SUCCESS / FAILED
```
- 提供 `getTaskStatus(taskId)` 查询接口
- 支持任务取消、重试
